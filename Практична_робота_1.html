1. Мета роботи

Сформувати практичні навички проєктування архітектури програмної системи з використанням принципів чистої архітектури та Domain-Driven Design, а також навички моделювання предметної області та визначення bounded context.

2. Предметна область

Для виконання роботи обрано предметну область «Інтернет-магазин книг» (BookStore). Система дозволяє вести каталог книг, реєструвати клієнтів та обробляти замовлення.

Основні бізнес-процеси:

  • Додавання книг до каталогу з вказанням ціни та кількості на складі
  • Реєстрація клієнтів
  • Створення замовлень з перевіркою наявності книг на складі
  • Підтвердження та скасування замовлень

3. Архітектура проєкту

3.1. Поділ на шари

Проєкт побудований відповідно до принципів чистої архітектури та складається з 4 шарів, кожен з яких реалізований як окремий проєкт у рішенні (solution):

Шар (проєкт) Відповідальність Залежить від
BookStore.Domain Доменна модель: сутності, value objects, інтерфейси репозиторіїв. Бізнес-логіка та правила. Нічого (ядро системи)
BookStore.Application Прикладні сервіси (use cases), DTO для обміну даними між шарами. Domain
BookStore.Infrastructure Реалізації репозиторіїв (доступ до даних). Тут — In-Memory сховище. Domain, Application
BookStore.WebAPI REST API контролери, реєстрація залежностей (DI), точка входу. Application, Infrastructure

3.3. Напрям залежностей

  ┌─────────────────────────┐
  │   WebAPI (Presentation) │
  └──────────┬──────────────┘
             │ залежить від
             ▼
  ┌─────────────────────────┐       ┌─────────────────────────┐
  │     Application         │       │    Infrastructure       │
  │  (сервіси, use cases)   │       │ (реалізація репозиторіїв)│
  └──────────┬──────────────┘       └──────────┬──────────────┘
             │ залежить від                    │ залежить від
             ▼                                 ▼
  ┌────────────────────────────────────────────────────────────┐
  │                     Domain (ядро)                          │
  │        Сутності, Value Objects, інтерфейси                 │
  │              НЕ ЗАЛЕЖИТЬ НІ ВІД ЧОГО                       │
  └────────────────────────────────────────────────────────────┘

Ключовий принцип: залежності спрямовані лише всередину — зовнішні шари залежать від внутрішніх, але ніколи навпаки. Доменний шар є повністю незалежним.

4. Доменна модель (DDD)

4.1. Сутності (Entity)

Сутність — об'єкт з унікальним ідентифікатором (Id), який зберігається протягом усього життєвого циклу.

СутністьПризначенняКлючові бізнес-методи
Book Книга в каталозі DecreaseStock() — зменшити кількість на складі
IncreaseStock() — поповнити склад
Customer Клієнт магазину Валідація при створенні (ПІБ, Email)
Order Замовлення (Aggregate Root) AddItem() — додати позицію
Confirm() — підтвердити
Cancel() — скасувати
GetTotalPrice() — загальна вартість
OrderItem Позиція замовлення GetTotalPrice() — вартість позиції

4.2. Value Objects (Об'єкти-значення)

Value Object — об'єкт без ідентифікатора, який порівнюється за значенням своїх полів. Два об'єкти з однаковими полями вважаються рівними.

Value ObjectПоляПризначення
Address City, Street, Building Адреса доставки замовлення
Money Amount, Currency Грошова сума з валютою (за замовчуванням UAH)

4.3. Агрегат (Aggregate)

Order є коренем агрегату (Aggregate Root). Він керує колекцією OrderItem. Зовнішній код не може змінювати позиції замовлення напряму — лише через методи Order (наприклад, AddItem()). Колекція Items доступна тільки для читання (IReadOnlyCollection).

4.4. Інверсія залежностей (Dependency Inversion)

Інтерфейси репозиторіїв оголошені у Domain (внутрішній шар), а їх реалізації — в Infrastructure (зовнішній шар). Завдяки цьому доменний шар не знає, як зберігаються дані.

Інтерфейс (Domain)Реалізація (Infrastructure)
IBookRepositoryInMemoryBookRepository
IOrderRepositoryInMemoryOrderRepository
ICustomerRepositoryInMemoryCustomerRepository

5. Bounded Contexts

У системі виділено три обмежених контексти, кожен з яких має власну доменну модель та бізнес-правила:

Bounded ContextВідповідальністьСутності
Catalog Управління каталогом книг, ціноутворення, облік на складі Book, Money
Ordering Створення, підтвердження та скасування замовлень Order, OrderItem, Address, OrderStatus
Customer Management Реєстрація та зберігання даних клієнтів Customer

5.1. Взаємодія між Bounded Contexts

  ┌──────────────────┐         ┌──────────────────┐
  │     Catalog      │         │    Customer       │
  │                  │         │    Management     │
  │   Book, Money    │         │    Customer       │
  └────────▲─────────┘         └────────▲──────────┘
           │                            │
           │ BookId                     │ CustomerId
           │ (контракт)                 │ (контракт)
           │                            │
  ┌────────┴────────────────────────────┴──────────┐
  │                  Ordering                       │
  │         Order, OrderItem, Address               │
  └─────────────────────────────────────────────────┘

Ordering → Catalog: при створенні замовлення перевіряється наявність книги на складі та зменшується кількість. Контексти зв'язані через BookId, а не через прямі посилання на об'єкти.

Ordering → Customer Management: при створенні замовлення перевіряється існування клієнта. Зв'язок через CustomerId.

Такий підхід дозволяє уникнути змішування бізнес-логіки різних підсистем і забезпечує незалежний розвиток кожного контексту.

6. Лістинги коду

6.1. Доменний шар — сутність Book (Book.cs)

using BookStore.Domain.ValueObjects;

namespace BookStore.Domain.Entities;

public class Book
{
    public Guid Id { get; private set; }
    public string Title { get; private set; }
    public string Author { get; private set; }
    public string ISBN { get; private set; }
    public Money Price { get; private set; }
    public int StockQuantity { get; private set; }

    public Book(Guid id, string title, string author,
                string isbn, Money price, int stockQuantity)
    {
        if (string.IsNullOrWhiteSpace(title))
            throw new ArgumentException("Назва книги не може бути порожньою.");
        if (string.IsNullOrWhiteSpace(author))
            throw new ArgumentException("Автор не може бути порожнім.");
        if (stockQuantity < 0)
            throw new ArgumentException("Кількість не може бути від'ємною.");

        Id = id;
        Title = title;
        Author = author;
        ISBN = isbn;
        Price = price;
        StockQuantity = stockQuantity;
    }

    public void DecreaseStock(int quantity)
    {
        if (quantity <= 0)
            throw new ArgumentException("Кількість має бути більше нуля.");
        if (StockQuantity < quantity)
            throw new InvalidOperationException("Недостатньо книг на складі.");
        StockQuantity -= quantity;
    }

    public void IncreaseStock(int quantity)
    {
        if (quantity <= 0)
            throw new ArgumentException("Кількість має бути більше нуля.");
        StockQuantity += quantity;
    }
}

6.2. Доменний шар — агрегат Order (Order.cs)

using BookStore.Domain.Enums;
using BookStore.Domain.ValueObjects;

namespace BookStore.Domain.Entities;

public class Order
{
    public Guid Id { get; private set; }
    public Guid CustomerId { get; private set; }
    public DateTime CreatedAt { get; private set; }
    public OrderStatus Status { get; private set; }
    public Address DeliveryAddress { get; private set; }

    private readonly List<OrderItem> _items = new();
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();

    public Order(Guid id, Guid customerId, Address deliveryAddress)
    {
        Id = id;
        CustomerId = customerId;
        DeliveryAddress = deliveryAddress;
        CreatedAt = DateTime.UtcNow;
        Status = OrderStatus.Created;
    }

    public void AddItem(Guid bookId, string bookTitle,
                        int quantity, Money unitPrice)
    {
        if (Status != OrderStatus.Created)
            throw new InvalidOperationException(
                "Не можна змінювати підтверджене замовлення.");
        var item = new OrderItem(Guid.NewGuid(), bookId,
                                 bookTitle, quantity, unitPrice);
        _items.Add(item);
    }

    public decimal GetTotalPrice() =>
        _items.Sum(item => item.GetTotalPrice());

    public void Confirm()
    {
        if (Status != OrderStatus.Created)
            throw new InvalidOperationException(
                "Замовлення можна підтвердити лише зі статусу Created.");
        if (!_items.Any())
            throw new InvalidOperationException(
                "Не можна підтвердити порожнє замовлення.");
        Status = OrderStatus.Confirmed;
    }

    public void Cancel()
    {
        if (Status == OrderStatus.Delivered)
            throw new InvalidOperationException(
                "Не можна скасувати доставлене замовлення.");
        Status = OrderStatus.Cancelled;
    }
}

6.3. Доменний шар — Value Object Address (Address.cs)

namespace BookStore.Domain.ValueObjects;

public class Address
{
    public string City { get; }
    public string Street { get; }
    public string Building { get; }

    public Address(string city, string street, string building)
    {
        if (string.IsNullOrWhiteSpace(city))
            throw new ArgumentException("Місто не може бути порожнім.");
        if (string.IsNullOrWhiteSpace(street))
            throw new ArgumentException("Вулиця не може бути порожньою.");
        if (string.IsNullOrWhiteSpace(building))
            throw new ArgumentException("Будинок не може бути порожнім.");
        City = city;
        Street = street;
        Building = building;
    }

    // Value Object порівнюється за значенням
    public override bool Equals(object? obj)
    {
        if (obj is not Address other) return false;
        return City == other.City
            && Street == other.Street
            && Building == other.Building;
    }

    public override int GetHashCode() =>
        HashCode.Combine(City, Street, Building);
}

6.4. Прикладний шар — сервіс OrderService (OrderService.cs)

using BookStore.Application.DTOs;
using BookStore.Application.Interfaces;
using BookStore.Domain.Entities;
using BookStore.Domain.Interfaces;
using BookStore.Domain.ValueObjects;

namespace BookStore.Application.Services;

public class OrderService : IOrderService
{
    private readonly IOrderRepository _orderRepository;
    private readonly IBookRepository _bookRepository;
    private readonly ICustomerRepository _customerRepository;

    public OrderService(IOrderRepository orderRepository,
        IBookRepository bookRepository,
        ICustomerRepository customerRepository)
    {
        _orderRepository = orderRepository;
        _bookRepository = bookRepository;
        _customerRepository = customerRepository;
    }

    public async Task<OrderDto> CreateOrderAsync(CreateOrderDto dto)
    {
        var customer = await _customerRepository.GetByIdAsync(dto.CustomerId);
        if (customer == null)
            throw new ArgumentException("Клієнта не знайдено.");

        var address = new Address(dto.City, dto.Street, dto.Building);
        var order = new Order(Guid.NewGuid(), dto.CustomerId, address);

        foreach (var itemDto in dto.Items)
        {
            var book = await _bookRepository.GetByIdAsync(itemDto.BookId);
            if (book == null)
                throw new ArgumentException("Книгу не знайдено.");

            book.DecreaseStock(itemDto.Quantity);
            await _bookRepository.UpdateAsync(book);
            order.AddItem(book.Id, book.Title,
                          itemDto.Quantity, book.Price);
        }

        await _orderRepository.AddAsync(order);
        return MapToDto(order);
    }
    // ... інші методи
}

6.5. Інфраструктурний шар — InMemoryBookRepository

using BookStore.Domain.Entities;
using BookStore.Domain.Interfaces;

namespace BookStore.Infrastructure.Repositories;

public class InMemoryBookRepository : IBookRepository
{
    private readonly List<Book> _books = new();

    public Task<Book?> GetByIdAsync(Guid id)
    {
        var book = _books.FirstOrDefault(b => b.Id == id);
        return Task.FromResult(book);
    }

    public Task<IEnumerable<Book>> GetAllAsync() =>
        Task.FromResult<IEnumerable<Book>>(_books.ToList());

    public Task AddAsync(Book book)
    {
        _books.Add(book);
        return Task.CompletedTask;
    }

    public Task UpdateAsync(Book book) => Task.CompletedTask;

    public Task DeleteAsync(Guid id)
    {
        var book = _books.FirstOrDefault(b => b.Id == id);
        if (book != null) _books.Remove(book);
        return Task.CompletedTask;
    }
}

6.6. Презентаційний шар — BooksController

using Microsoft.AspNetCore.Mvc;
using BookStore.Application.DTOs;
using BookStore.Application.Interfaces;

namespace BookStore.WebAPI.Controllers;

[ApiController]
[Route("api/[controller]")]
public class BooksController : ControllerBase
{
    private readonly IBookService _bookService;

    public BooksController(IBookService bookService)
    {
        _bookService = bookService;
    }

    [HttpGet]
    public async Task<IActionResult> GetAll()
    {
        var books = await _bookService.GetAllAsync();
        return Ok(books);
    }

    [HttpGet("{id}")]
    public async Task<IActionResult> GetById(Guid id)
    {
        var book = await _bookService.GetByIdAsync(id);
        if (book == null) return NotFound();
        return Ok(book);
    }

    [HttpPost]
    public async Task<IActionResult> Create([FromBody] CreateBookDto dto)
    {
        var book = await _bookService.CreateAsync(dto);
        return CreatedAtAction(nameof(GetById),
            new { id = book.Id }, book);
    }
}

7. Відповіді на контрольні питання

1. У чому полягає основна ідея чистої архітектури?

Чиста архітектура передбачає поділ програмної системи на шари з чітко визначеними відповідальностями, де залежності спрямовані від зовнішніх шарів до внутрішніх. Основна ідея — бізнес-логіка (доменний шар) є повністю незалежною від фреймворків, баз даних та інтерфейсів користувача. Це робить систему тестованою, підтримуваною та гнучкою до змін.

2. Що таке Domain-Driven Design та яка його роль в архітектурі ПЗ?

Domain-Driven Design — це підхід до розробки програмного забезпечення, що зосереджується на глибокому моделюванні предметної області. Він допомагає перенести реальні бізнес-процеси в код за допомогою сутностей (Entity), об'єктів-значень (Value Object), агрегатів (Aggregate) та обмежених контекстів (Bounded Context). Роль DDD — забезпечити, щоб структура коду відображала бізнес-логіку, а не була прив'язана до технічних деталей реалізації.

3. Яке призначення bounded context?

Bounded context визначає межі застосування певної доменної моделі. Він дозволяє уникнути семантичних конфліктів між різними частинами системи. Наприклад, сутність «Клієнт» у контексті замовлень та у контексті маркетингу може мати різну структуру та поведінку. Кожен bounded context має власну модель, а взаємодія між контекстами здійснюється через чітко визначені контракти (наприклад, через ідентифікатори).

4. Які залежності дозволені між шарами системи?

Залежності спрямовані від зовнішніх шарів до внутрішніх: WebAPI → Application → Domain. Інфраструктурний шар також залежить від Domain. Доменний шар не залежить від жодного іншого шару — це ядро системи. Взаємодія між шарами здійснюється через абстракції (інтерфейси), що забезпечує слабку зв'язаність та можливість заміни реалізацій без зміни бізнес-логіки.

5. Чому доменна модель повинна бути ізольованою від інфраструктури?

Ізоляція доменної моделі від інфраструктури дає кілька переваг: (1) можливість тестувати бізнес-логіку без залежності від бази даних та фреймворків; (2) можливість замінювати інфраструктурні компоненти (наприклад, перейти з In-Memory сховища на SQL Server) без зміни бізнес-логіки; (3) зменшення зв'язаності — зміни в базі даних або API не впливають на доменну логіку; (4) підвищення читабельності коду, оскільки бізнес-правила зосереджені в одному місці.

8. Висновки

У ході виконання практичної роботи було спроєктовано архітектуру програмної системи «Інтернет-магазин книг» з використанням принципів чистої архітектури та Domain-Driven Design.

Було створено проєкт ASP.NET Core з поділом на 4 шари: Domain, Application, Infrastructure та WebAPI. Доменний шар містить сутності (Book, Customer, Order, OrderItem), об'єкти-значення (Address, Money) та інтерфейси репозиторіїв, при цьому він не залежить від жодного зовнішнього компонента.

Визначено 3 bounded contexts: Catalog (каталог книг), Ordering (управління замовленнями) та Customer Management (управління клієнтами). Взаємодія між контекстами здійснюється через ідентифікатори (BookId, CustomerId), що забезпечує слабку зв'язаність.

Реалізовано принцип інверсії залежностей: інтерфейси репозиторіїв оголошені в доменному шарі, а їх реалізації — в інфраструктурному, що дозволяє легко замінити спосіб зберігання даних без зміни бізнес-логіки.
